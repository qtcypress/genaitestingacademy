Careers

From manual tester to
AI testing engineer

What actually changes, which of your existing skills transfer unchanged, what to learn and in what order, and how to get the first piece of evidence that you can do this work. Written for people who already test software, not for people starting from nothing.

The one thing that changes

Every test you have ever written rests on an assumption so basic it is rarely stated: the same input produces the same output, so a difference means a defect. Generative AI breaks that assumption and nothing else. The model returns a different answer to the same question on Tuesday than it did on Monday, and both answers can be correct. Your assertion has nowhere to anchor.

So the work moves from comparing output to an expected result to defining what acceptable means and then checking it holds. That is a different sentence in a bug report and a different conversation with a developer, but it is still testing, and it is still the same instinct — this thing claims to work; let us find out where it does not.

What transfers, unchanged

More than people expect, and this is the part the career-change content usually gets wrong by implying you are starting over.

Adversarial thinking

The habit of reading a requirement and immediately thinking "what if it is empty, enormous, in another language, or deliberately hostile" is the single most valuable thing in AI testing, and it is exactly what a good manual tester already does. Prompt injection testing is adversarial thinking pointed at a new surface.

Writing a defect someone will act on

Reproduction steps, evidence, expected versus actual, severity argued rather than asserted. This gets harder with AI features, because "it said something wrong once" is not a reproducible defect. The people who can already write a convincing bug report have a real advantage.

Knowing the domain

Whether an answer about a mortgage, a prescription or a refund policy is actually correct requires knowing the domain, and you do. This is the skill a machine-learning engineer joining your team does not have, and it is why testers are the right people for this work rather than a stopgap.

Scepticism about metrics

Anyone who has watched a team celebrate 90% test coverage over a broken feature already understands the central trap of AI evaluation, where a confident score can sit on top of a system that does not work.

What to learn, in order

The order matters more than the list. Most people try to learn the tools first, find that the tools assume concepts they do not have, and conclude the subject is harder than it is.

1. Enough Python to read and change code

Not software engineering — the ability to read a script, change a value, run it and understand the error. If you already automate in any language this is a week. If you do not code at all, this is the longest step and there is no way around it: every evaluation framework is a library you import. The Python track starts at variables, and the free Git and GitHub module covers the version control every one of those repositories lives in.

2. How a RAG application is wired

Retrieval, then generation. Most AI features in real companies are RAG rather than a bare model, and almost every interesting failure is a retrieval failure wearing a generation costume. Understanding the two halves is what lets you diagnose rather than describe.

3. Evaluation before tooling

Faithfulness, relevance, groundedness, precision and recall on retrieval — what each one measures and what it misses. Learn this before Promptfoo or DeepEval, because the tools are thin wrappers around these ideas and are baffling without them. The FAQ covers each metric and the trap in reading it alone.

4. One evaluation tool, properly

Then pick one and get it into a pipeline that fails a build. One tool understood well beats four tried once, and "I put LLM evaluations in CI" is a sentence that gets interviews.

5. Adversarial testing

Prompt injection, both direct and the indirect kind that arrives inside a retrieved document, jailbreaks, data leakage, and what happens when an agent is given a tool it should refuse to use. This is where experienced testers pull ahead fastest.

6. Agents, last

Tool selection, loops, budgets, hand-offs. Genuinely harder, genuinely newer, and the area where the least settled practice exists — which also means nobody expects you to have it on day one.

Is manual testing still a good career?

Yes, and the version of this question worth answering is narrower than the one usually asked. What is disappearing is not testing but the pure execution role — running a scripted regression pass by hand, where the value was in the hours rather than the judgement. That erosion started long before generative AI and is mostly automation's doing.

What is not disappearing is deciding what correct means, arguing severity, designing the case nobody thought of, and taking responsibility for shipping. AI features make that work more valuable rather than less, because there is now a category of software whose output nobody can fully predict and somebody has to be accountable for whether it is fit to release. The honest framing is not "manual testing is dead" but "the execution part was always the replaceable part".

About money

This page deliberately quotes no salary figures, and the reason is worth stating because almost every competing page does. The numbers in circulation for AI testing roles come from self-reported aggregator data on small samples; across sources they differ by a factor of three for the same title and city, and they are out of date by the time they are published. A range invented here would make this page look authoritative and would not survive contact with a real offer.

What works instead: search your own market's live listings for the actual title — AI quality engineer, LLM evaluation engineer, AI testing engineer — and read the twenty most recent. Many list a band. That tells you what your city pays this quarter, which no article can. Ask a recruiter who places into these roles; they have better data than any public site. What can be said generally is that the differential comes from scarcity rather than from the title, so it rewards demonstrable evidence rather than a course certificate on its own.

The first piece of evidence

The difficulty in this transition is not learning; it is proving. Nobody will give you AI testing work on the strength of having studied AI testing, and the gap is usually closed by one of two things.

The first is the AI feature already in your current company. Most organisations have shipped one and almost none have a considered test approach for it. Writing that approach — even three pages on what acceptable means and how you would check it — is both real work and the exact artefact that gets you the role internally, which is the easiest route by a distance.

The second is a project you can show. Not a certificate: a repository with an evaluation suite, a golden dataset, a documented adversarial finding, and an honest write-up of what it does not cover. That last part matters more than it sounds — knowing the limits of your own test suite is the thing that reads as experience. The capstone projects exist for this, and the deliberately poisoned RAG application in particular produces findings worth writing up.

Where to start

If you can already read code, start at evaluation and skip the Python track. If you cannot, start with Python — it is the actual prerequisite and no amount of conceptual understanding substitutes for it.
