1Friday, 6pm, and nobody knows which file is real

Two testers share a folder. Asha edits suite.xlsx; so does Bala, from the copy he took on Tuesday. He saves last. Her morning disappears — silently, with no error and nothing to point at. By Friday the folder holds suite_final.xlsx, suite_final_v2.xlsx and suite_final_REAL_use_this.xlsx, and the only person who knows which is current has gone home.

Every feature of Git is an answer to some version of that evening. Not an abstraction — an answer. A version control system records every change to a set of files: who, what, when, and the ability to return to any earlier state. History, rollback, parallel work that merges instead of overwriting, and a full backup on every machine that has a copy.

KindWhere history livesExamples
LocalOne computerRCS
CentralizedOne server everyone depends onSVN, CVS, Perforce
DistributedEvery developer has the whole historyGit, Mercurial

Distributed is why Git works on a plane: your laptop holds the entire history, so committing, branching and reading the log need no network at all. Only sharing does. Platforms built around Git — GitHub, GitLab, Bitbucket, Azure Repos — are where that sharing happens.

2The four places — the whole of Git, really

Git stores snapshots, not differences. Each snapshot is a commit, with a unique 40-character ID and a pointer to its parent, which is what makes history a chain. A branch is nothing more than a movable label pointing at one commit, and HEAD is the label saying which branch you are on. That is the entire data model.

The part that trips everyone is not the model but the plumbing: your work passes through four places, and three of them are invisible. Move the file yourself and watch git status change.

Working directorythe folder you actually edit
Staging areachanges picked for the next commit
Local repositorythe .git folder — your history
RemoteGitHub, shared with everyone

The staging area is the one beginners skip past and the one worth understanding. It exists so that a commit can be smaller than everything you changed: fix a bug and a typo in the same hour, stage only the bug fix, and the history records one intention per commit. That is what makes git log readable a year later, and it is why git add is a separate step rather than an annoyance.

Coming the other way: git fetch downloads remote work without touching yours, git pull is fetch plus merge, and git switch loads a different branch into your working directory. Inside .git you will find objects/ (the snapshots), refs/ (the branch labels), index (the staging area) and config.

3Installing, and telling Git who you are

Windows

Download from git-scm.com/downloads. Keep the defaults with two exceptions: set the default branch name to main, and choose Git from the command line and 3rd-party software for PATH. You will get Git Bash, a proper terminal, on the right-click menu.

macOS and Linux

# macOS
brew install git

# Ubuntu / Debian
sudo apt update && sudo apt install git -y

Then tell it who you are — this goes into every commit, permanently

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --list

Use the email your GitHub account uses, or your commits will not be linked to your profile. It is a two-minute fix now and a tedious one later, because the name and address are baked into every commit you have already made.

5Branching, drawn

"A branch is a movable label" is true and useless until you see the label move. Build the graph a step at a time and watch where main and feature point after each one.

Two things worth taking from that. A branch costs nothing — it is a label, not a copy of your files, which is why branching for a two-line change is normal rather than excessive. And a merge commit has two parents, which is how Git remembers that two lines of work came back together.

6GitHub, and what it adds

Git is software on your computer. GitHub is a website that stores Git repositories and adds the things teams need around them. Keeping the two apart in your head saves a great deal of confusion later: Git works perfectly with no GitHub account at all.

The pull request, which is the part that matters at work

You push a branch, open a pull request, and somebody reads the change before it reaches main. That is the whole ritual, and nearly every professional team runs on it. The reviewer sees exactly what changed, comments on specific lines, and approves or asks for changes; then the branch merges and is deleted. Small pull requests get reviewed properly; large ones get approved without being read, which is worth knowing before you open one with forty files in it.

7GitHub Desktop, for when buttons are faster

GitHub Desktop does Git with buttons. It is a genuinely good way to work, not a beginner's crutch — reviewing your own diff before committing is easier there than in a terminal. Install it from desktop.github.com, sign in, and set the same name and email you configured in act 3. Each task below shows the equivalent command, because the two should sit together in your head.

8The conflict, which is not a disaster

A conflict means two branches changed the same lines and Git will not guess which one you meant. That is the whole of it. Git stops, marks the spot, and waits — it has not lost anything and nothing is broken. Most of the fear around conflicts comes from only ever meeting one during a crisis, so meet one now instead.

Resolving a conflict is nothing more than editing the file until it says what you want and deleting the three marker lines. Then git add the file to tell Git you have dealt with it, and git commit to finish the merge. If it goes wrong at any point, git merge --abort puts everything back exactly as it was.

9Mastery — the commands that save an afternoon

Rebase, and when not to

A merge joins two lines of history and records that it happened. A rebase replays your commits on top of another branch, producing a straight line as though you had started from the latest code. Rebase gives a cleaner log; merge gives an honest one. Either is defensible, and teams usually just pick one.

The rule that matters: only rebase commits nobody else has. Rebasing rewrites commits, giving them new IDs, so anyone who already pulled the old ones now has a history that disagrees with yours — and the fix is painful. On your own unpushed branch, rebase freely. On a shared branch, do not.

Stash — for the interruption

You are mid-change and something urgent lands on another branch. git stash shelves the work and leaves you clean; switch, deal with it, come back, git stash pop. Name them with git stash push -m "wip: cart" if you expect more than one, because a list of unlabelled stashes is its own small problem.

Cherry-pick — one commit, somewhere else

git cherry-pick a1b2c3 copies a single commit onto your current branch. Useful for a fix that needs to reach a release branch without the five other commits sitting beside it. It makes a copy with a new ID rather than moving anything.

Undo — the four different ones

SituationCommandWhat happens
Edited a file, want the last committed version backgit restore app.jsYour edit is gone for good. Nothing else changes.
Staged something by mistakegit restore --staged app.jsUnstaged, edit kept.
Committed too early, want to redo itgit reset --soft HEAD~1Commit undone, changes back in staging. Local only.
A bad commit is already pushedgit revert a1b2c3A new commit that undoes it. Safe on shared branches.

The distinction worth internalising is the last two. reset rewrites history and is fine while the commit is still only yours. revert adds to history and is the correct choice once anyone else could have pulled it. Reaching for reset on a shared branch is how people create the afternoon they then spend fixing.

And when you are sure you have lost work

You almost certainly have not. git reflog lists every position HEAD has held, including commits no branch points at any more — after a bad reset, a botched rebase, a deleted branch. Find the ID, then git switch -c rescue a1b2c3. Git keeps unreachable commits for weeks. This one command has saved more work than any other in this list, and almost nobody learns it until the day they need it.

The loop you will actually use every day

git pull → edit → git status → git add . → git commit -m "message" → git push. Nine commands out of ten you will ever type are in that line. The rest of this page is for the days when something goes sideways.
