Agents

Agentic AI testing
when the model stops answering and starts acting

An agent plans, calls tools, loops, delegates, spends money, sends messages, and reads data someone else wrote. Each of those is a failure mode that an evaluation scoring the final answer will never see. This is what changes, and how to test it.

The one shift everything else follows from

When you test a single prompt, the thing you judge is a piece of text. When you test an agent, the text is often the least interesting part of the run. The agent reached that answer by choosing tools, reading what came back, and deciding what to do next — and it can arrive at a perfectly good answer through a route that was expensive, unsafe, or simply lucky. Run it again and the route changes.

So the unit of testing moves from the output to the trajectory: the ordered record of what was called, with what arguments, how many times, what was refused, and what happened when something failed. Outcome-only testing cannot tell a correct answer reached safely from a correct answer reached by calling a payment tool four times and getting away with it. In production those are not the same system, and only one of them is one you want.

The six things that actually break

Tool selection

Given an ambiguous request, does it reach for the right tool — and for none at all when none applies? The interesting case is the near-miss: two tools whose descriptions overlap, where picking either looks reasonable and only one is correct.

Arguments

Well-formed, in range, and derived from what the user actually said. Vague phrasing is where agents invent: a date nobody gave, a quantity rounded up, an identifier that looks plausible and belongs to someone else.

Loops and budgets

Make a tool fail on purpose and watch. Does it stop, or retry until something external cuts it off? A prompt asking it to be careful is not a control. A hard cap on iterations, tool calls, tokens and money is.

Delegation

When one agent hands to another, what travels with it? Context gets lost, and sometimes the opposite — something sensitive travels that should not. Both are hand-off defects and neither is visible in the final answer.

Untrusted results

An agent reads tool output and acts on it. If that output can contain text someone else wrote, you have an instruction channel you did not design. This is indirect prompt injection, and agents are where it gets expensive, because the payload can reach something that spends money.

Refusals, in both directions

Declining a destructive call on a vague instruction is the control working. Over-refusal is also a defect, just a quieter one. The suite needs paired sets — must-act and must-refuse — and both halves have to pass before either number means anything.

Agentic RAG: retrieval becomes a decision

Ordinary RAG retrieves on every question and puts the results in the prompt. Agentic RAG lets the model decide: whether to search at all, what to search for, which source to use, whether what came back was good enough, and whether to go again with a better query. That is a real improvement in capability and it moves the thing you test. Retrieval precision still matters, but now so does judgement about retrieval.

Four cases carry most of the value. A question the model can answer from its own knowledge — does it skip the search, or burn a call and a second of latency on it? A question needing two different sources — does it make both calls, or answer from the first? A first search that returns nothing useful — does it reformulate, or answer from the noise it got? And a question the corpus simply does not cover — does it say so? That last one is where the familiar metrics mislead most, because faithfulness scores perfectly well against whatever happened to come back.

MCP, and the trust it quietly changes

Model Context Protocol standardises how an agent connects to tools and data, so any client that speaks it can use any server without a bespoke integration. That part is genuinely useful. The testing interest is in what it does to trust, and there are three things worth holding on to.

Tool descriptions are prompt. The text describing a tool reaches the model, so a compromised or malicious server can put instructions in it — tool poisoning. Tool results are untrusted input, and an agent that treats whatever a server returns as fact has handed its behaviour to whoever runs that server. Grants drift wider than the task, because a connection added for one job stays available for every later one, so the question is not "does this tool work" but "what can it reach when the model is confused or steered".

Servers also update independently of you, so a tool that behaved one way when you tested it can behave differently tomorrow with nothing changed on your side. The test that finds all of this is a deliberately hostile MCP server of your own: have it return a result containing an instruction, and watch whether the agent reports it or obeys it.

What a suite looks like in practice

Three layers, and most teams only build the first. Outcome: did the run achieve the goal — necessary, insufficient, and the easiest to write. Trajectory: assertions on the route, read like a log. This tool exactly once; this one never for this input; the budget check before the booking call; no tool retried more than three times. Boundary: the suite run against a hostile environment — tools that fail, tools that return injected text, budgets set below the cost of the task, instructions that should be refused.

The boundary layer is the one that changes what you ship, and it is the one that cannot be written from a specification. It needs a system you are allowed to attack.

The system this is taught on

An orchestrator plans a whole trip inside a budget and delegates to nine specialist agents over an MCP tool server. It is deliberately the smallest system that produces every agentic failure mode at once: it plans, calls tools, loops, delegates, spends money, messages people, and reads data an attacker could have written. Alongside it sits a retrieval assistant built five times over, each version adding a layer, so a change in behaviour can be traced to a specific decision rather than guessed at.

Questions people ask about testing agents

What is agentic AI testing?

Testing a system where a model does not just answer but acts — it chooses tools, calls them, reads the results, decides what to do next, and often delegates to other agents. The shift from ordinary LLM testing is that the output you judge is no longer a piece of text. It is a sequence of decisions, and a run can reach a perfectly good final answer through a route that was expensive, unsafe or lucky. So an agentic test suite asserts on the path as well as the destination: which tool was chosen, with what arguments, how many times, what was refused, and what the agent did when a tool failed.

How is testing an AI agent different from testing an LLM?

A single prompt has one failure mode that matters: the text is wrong. An agent adds failure modes that have nothing to do with text quality. It can pick the wrong tool, construct arguments that are out of bounds, loop until something external stops it, delegate to a sub-agent and lose context in the hand-off, act on a tool result that an attacker wrote, or spend real money doing any of it. None of those show up in an evaluation that only scores the final answer, which is why teams that carry their LLM test approach straight across find their agent suite is green while the system does alarming things in staging.

What is agentic RAG, and how do you test it?

In ordinary RAG, retrieval is a fixed step: every question triggers a search, and the results go into the prompt. In agentic RAG the model decides — whether to retrieve at all, what to search for, which source to use, whether the results were good enough, and whether to search again with a different query. That makes retrieval a decision rather than a step, and decisions are what you test. Four cases carry most of the value: a question answerable from the model's own knowledge (does it skip retrieval, or search pointlessly?); a question needing two different sources (does it make both calls?); a first search that returns nothing useful (does it reformulate, or answer from the noise?); and a question nothing in the corpus covers (does it say so?). The last one is where ordinary RAG metrics mislead most, because faithfulness scores well against whatever came back.

How do you test an MCP agent?

Model Context Protocol standardises how an agent connects to tools, and the testing interest is entirely in what it changes about trust. Tool descriptions are prompt: the text describing a tool reaches the model, so a compromised server can put instructions there. Tool results are untrusted input, and an agent that treats whatever a server returns as fact has handed its behaviour to that server. Grants are usually too broad, because a connection added for one task stays available for every later one. And servers update independently, so a tool that behaved one way when you tested it can behave differently tomorrow with no change on your side. The test that finds all of this is a deliberately hostile MCP server of your own: have it return a result containing an instruction and watch whether the agent obeys it.

What is trajectory testing?

Asserting on the route the agent took, not only the answer it produced. A trajectory is the ordered record of tool calls, arguments, results and decisions in one run. You test it the way you would test a log: this tool should appear exactly once; this one should never appear for this input; the budget check should precede the booking call; no tool should be retried more than three times. It matters because outcome-only testing cannot distinguish a correct answer reached safely from a correct answer reached by calling a payment tool four times and getting lucky — and in production those are not the same system.

How do you stop an AI agent looping or overspending?

Limits that live outside the model, and tests that prove they hold. A prompt asking an agent to be careful is not a control; a hard cap on iterations, on tool calls per run, on total tokens and on money is. Test them by making the environment hostile rather than by hoping: force a tool to fail repeatedly and assert the agent stops rather than retrying forever; set the budget below the cost of the task and assert it halts and reports instead of proceeding. The failure to look for is an agent that treats a limit as an obstacle and works around it — by splitting a purchase, say — which is behaviour you only ever see if you test at the boundary.

Is a refusal from an agent a bug?

Usually it is the control working, and logging it as a defect is how teams train a system towards the behaviour they least want. When an agent declines to call a destructive tool on a vague instruction, that is correct. The real measure needs both directions, because over-refusal is also a defect: an agent that refuses ordinary requests is useless in a quieter way than one that is reckless. So the suite holds a paired set — prompts that must be acted on and prompts that must be refused — and both halves have to pass before either number means anything.
